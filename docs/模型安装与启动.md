# 模型安装与启动（板端 / 电脑端分工版）

> 架构依据：[docs/给方块识别同学.md](给方块识别同学.md)（2026-11-06 新结构）＋ 本机实测（2026-11-09 ~ 11-13，Windows + 有线网卡 `192.168.137.102`，开发板 `192.168.137.100`）。
> 权重清单见 [训练权重清单.md](训练权重清单.md)。

## 0. 一句话分工

**模型在电脑上跑，几何与执行在板端跑。** 电脑端只回答"方块在画面哪个像素"，坐标换算、够不够得着、会不会撞、要不要拒绝，全部由开发板计算并执行。

## 1. 计算分工（谁算什么）

| # | 步骤 | 跑在哪 | 代码 | 输入 → 输出 |
|---|---|---|---|---|
| 1 | 采图 / 冻结一帧 | **板端** | `board/camera.py`、`manipulation.capture()` | `/dev/video0` → JPEG ＋ 六关节真实读数 ＋ `frame_id` |
| 2 | 方块识别（YOLO） | **电脑** | `pc/block_vision/yolo_detector.py` | 原图 BGR → 四个颜色的框与置信度 |
| 3 | 顶面几何（HSV/四边形/中心） | **电脑** | `pc/block_vision/top_face.py` | 框 → 顶面四角 `corners` ＋ 中心 `center` ＋ `score` |
| 4 | 像素 → 三维坐标 | **板端** | `manipulation_geometry.locate()` | 四角 ＋ 内参 ＋ 冻结关节 → `xyz_mm` |
| 5 | 可达 / 碰撞 / 扫掠检查、生成计划 | **板端** | `build_plan()`、`manipulation_collision.py` | `xyz_mm` → 有限步数的关节目标 |
| 6 | ROS2 独立比对 | **板端**（同机纯计算） | `board/ros_planner.py` | 本地计划 vs ROS2 计划，不一致即拒绝 |
| 7 | 电脑端规划（可选，提速） | 电脑 | `pc/plan_server.py` | 只在显式启用时使用；本轮 `--no-pc-planner` 关闭 |
| 8 | 执行、逐步回读 | **板端** | `board/arm.py`（Arm_Lib / I2C） | 关节目标 → 舵机动作 ＋ 回读警告 |
| 9 | 界面与触发 | 两边 | `pc/vision_service.py`（PC 控制台）、`board/web/*`（网页） | 按钮 → HTTP |

数据流只有一条线：

```
板端相机 → 冻结帧(JPEG + 六关节) ──HTTP──▶ 电脑：YOLO + 顶面几何
                                        └─▶ 只回传像素 corners/center/score
板端收到 → 像素转坐标 → 可达/碰撞/扫掠 → ROS2 比对 → 执行前再读关节 → 逐关节下发
```

两条硬约束（AGENTS.md 第 75 条，板端强制校验）：

1. **电脑端只提交像素**（`source=vision`），提交关节角度会被拒绝；
2. **摄像头随机械臂移动**，所以识别必须用板端冻结的那一帧 ＋ 同时刻的六关节读数，不能用电脑摄像头。

耗时参考（实测）：电脑端识别 60–90 ms（顶面几何 1–2 ms）；板端规划 ＋ 4 步动作约 6–7 s。

### 2.3 启动（启动本身不运动）

在**板端 SSH 窗口**：

```bash
cd /root/jjt/board
/root/miniconda3/envs/ros-arm-env/bin/python -u -B start_service.py \
    --enable-real-control --enable-ros-planner --no-pc-planner
```

| 参数 | 含义 |
|---|---|
| `--enable-real-control` | 实机控制。**不加即模拟模式**，冻结帧里的六关节是假值（固定 90），不能用于真实抓取 |
| `--enable-ros-planner` | 启动 ROS2 纯计算节点做独立比对；不一致整体拒绝 |
| `--no-pc-planner` | 不用电脑端规划（默认地址 `192.168.137.101:8095`，与本机 `192.168.137.102` 不符，建议显式关闭） |

成功标志：`网页服务PID=…；启动不运动，实机启用=True`。

## 5. 授权与提交（顺序不能乱）

1. 网页 `http://192.168.137.100:8080/modes` 开模式：任务类型、放置点、次数、置信度下限、有效期 → 勾选 → **开启模式**（这一步就是本次会话的运动授权）。
2. 电脑端冻结一帧（`grasp_once.py --stage` 或控制台 ①）。
3. 人核对叠加图与关节读数后提交（`--submit` 或控制台 ②）。
4. 板端：定位 → 可达/碰撞/扫掠 → ROS2 比对 → **执行前再读六关节（与冻结值差 >1° 就拒绝）** → 逐关节下发。

| 接口 | 会不会动 |
|---|---|
| `GET /api/v1/health`、`/mode`、`/job`、`/frame.jpg` | 不动 |
| `POST /api/v1/block/frame` | 不动（读关节 ＋ 冻结图） |
| `POST /api/v1/block/target` | **会动**（会话已授权） |
| `POST /api/v1/gesture` | **会动** |
| `POST /api/v1/stop` | 只停后续步骤，已下发撤不回 |

## 6. 故障与处置

| 现象 | 原因 | 处置 |
|---|---|---|
| `ModuleNotFoundError: ultralytics` | 用 D 的 3.13 环境跑了 A 侧 | 换 `.venv-train` 的 python |
| `No module named 'mediapipe'` | 用 A 的 3.10 环境跑了 D 侧 | 换 `G:\venv-d313` |
| `unexpected model task/classes` | 权重类别顺序不是 blue/green/red/yellow | 换回包内 `best.pt` 并核对 SHA-256 |
| `没有已开启的 block_grasp 会话` | 网页还没开模式、已过期、次数用完或服务重启 | 回 `/modes` 重新开启 |
| `还没有可用的冻结结果` | 先点了 ②；或服务重启 / 冻结超 90 s / 会话换了 | 重新点 ①，再在 90 s 内点 ② |
| `这一帧没有可用候选（检出：…）` | 目标颜色不在画面里，或几何门没过 | 看括号里的颜色分数；换颜色/重摆，见下两行 |
| `review frame_boundary` | 方块被画面边缘裁掉 | 让整块在画面内，下缘留 ≥30 px |
| 候选 0 / `small_color_region`、`nonconvex…` | 顶面不完整、被遮挡、颜色区域太小 | 摆正方块、移开遮挡物、调整光照 |
| `取物点距底座…超出 133～319 毫米` | 方块太远（或太近） | 用 `reach_help.py` 看 319 mm 环，把中心放进环的近端 |
| `六关节读取不完整` / `无效读数：None` | 关节停在库读数窗口（脉宽 900–3100）之外，或 I2C 抖动 | 重读一次；持续失败则断电把该关节挪离限位 |
| `机械臂已离开冻结时的姿态` | 冻结到提交之间动过臂（>1°） | 重新冻结 |
| `端口 8099 已被占用` | 已经有一个控制台在跑 | 关掉旧实例，只留一个 |
| `cv2.calibrateHandEye` 不存在 | OpenCV 5.0.0 无此函数（板端 4.6 有） | 标定测试在板端跑 |

## 7. 已知限制

1. 两套电脑环境互斥（torch 2.7.1 vs 2.13.0、numpy 2.2.6 vs 2.4.3），不能合并；
2. 权重不入库，换机必须重新获取并校验；
3. 电脑端规划默认关闭（`.101:8095` 与本机 `.102` 不符）；
4. `pickup` 只夹取并抬升，结束保持夹持、不自动松爪；
5. 板端 `destinations` 为空时只能用 pickup，想连续抓放需先保存固定放置点；
6. 手势/语音模块只完成代码合并与冒烟，识别率需现场另做验收。
