# 项目结构说明（机械臂控制部分）

> 写给要讲解或接手本项目的 agent。范围是“机械臂控制”这一块（开发板端 `board/`、电脑端通信库与规划服务、工具、规则文件）；队友的方块识别、手势表情、语音模块只说明接口位置。
> 截至 2026-11-15（GitHub `main` 为 `8d1b036`）。更深的算法细节见文末“延伸阅读”，本文不重复。

---

## 1. 一句话概括

一台 DOFBOT 六自由度机械臂（6 号是夹爪），由一块开发板（`192.168.137.100`）驱动。开发板上运行一个 Python 网页服务（端口 8080）。人在网页上可以：

- 手动调关节、保存/执行六关节姿态按钮；
- 在冻结的摄像头画面上框选方块 → 自动定位、逆解、碰撞检查 → 确认后完整抓取/抓放；
- 相机标定；
- 点按钮跳舞（两套预设）；
- 开启“识别模式”，让电脑端的模型（方块识别 / 表情手势 / 语音）在授权范围内自动触发抓取或跳舞。

开发板算力弱，抓放的逆解与路径搜索可以交给网线另一端的电脑（`pc/plan_server.py`，端口 8095）计算，开发板再复核。

**核心设计原则：** 所有发往舵机的指令都经过同一个控制层校验；任何会动的操作都必须由用户在网页上当次明确确认（或开启有限次数的模式会话）；规则写在仓库根目录的两份规则文件里，并且代码在执行时会对规则文件做散列核对。

## 4. 分层结构

```
网页（board/web/*.html + *_ui.js）          电脑端（pc/run_*.py、vision_service.py、语音）
        │  POST + csrf 令牌                         │  HTTP /api/v1（会话编号）
        ▼                                           ▼
server.py 路由 ──► Control（control.py）◄── Modes（modes.py）
                     │   ▲                     │
                     │   └── Manipulation（manipulation_task.py）── 规划：manipulation_geometry.py 等
                     │                                              └── 可选：pc_planner.py → pc/plan_server.py
                     ▼
               arm.py：angle / timing / Controller.write / hardware_lock
                     ▼
                Arm_Lib（只在实机模式导入）
```

### 4.1 控制层 `board/arm.py`（所有运动的唯一出口）

- `angle(config, joint, value)`：编号 1～6、整数、在配置范围内（配置不得超出硬边界）。不合法直接抛错，**从不截断或夹紧**。
- `timing(config, start_move=False)`：用时 500～10000 ms、停稳 100～5000 ms。唯一例外：跳舞前回到竖直那一步 `start_move=True` 时用时必须恰好 300 ms（`START_MOVE_MS`）。
- `Controller.write(pairs, hold_ms=None, retries=0, start_move=False)`：整批先校验再逐关节写（关节间隔 20 ms），然后等待“用时+停稳”（或调用方给的更短 `hold_ms`，用于衔接）。`retries` 为单关节写入失败后重发同一绝对目标的次数（网页入口最多 2 次）。
- `Controller.read_report()`：逐关节读取，返回每关节 `read_ok/angle/error`。
- `checked_call`：Arm_Lib 的 I2C 异常只打印不抛出，所以把调用期间的 stdout/stderr 捕获下来，有输出就当失败（见第 10 节已知问题）。
- `hardware_lock()`：在 `data/.hardware.lock` 用排他创建文件实现跨进程锁，执行运动期间持有。
- 默认模拟；只有 `Controller(config, real=True)` 才导入 Arm_Lib。

### 4.2 调度层 `board/control.py`（`Control` 类）

- **两段式确认**：先“预览”生成一份完整参数 + 一次性 `token`（存在 `pending`，有过期时间），再 `execute({token, confirmed:True})` 才执行。网络重发同一 token 只返回原任务，不重复执行。
- **审计 `audit()`**：每次预览和执行前都对规则文件（`AGENTS.md`、`机械臂操作准则.md`）、核心代码（control/server/start_service/saved_states/camera/events/paths/arm、首页 html/js）和 `arm_config.json` 算 SHA-256；执行时与预览时不一致就拒绝。抓放和模式另有各自追加的审计文件。**所以改了规则文件或这些代码，进行中的预览/会话会失效。**
- **任务线程 `_work`**：持有硬件锁，在后台线程逐步下发；异常即停，不重试、不复位、不松爪。
- **请求去重**：`direct_jobs` / `manipulation_jobs` 按请求编号记录，且从 `logs/web_control.jsonl` 恢复，服务重启后同一编号也不会再执行。
- 直接入口：`direct_move`（单关节手动调整，点“确定”即授权）、`state_move`（姿态按钮，按保存的顺序逐关节）。
- 所有动作写入 `data/logs/web_control.jsonl`（kind：audit / accepted / sending / write_retry / read / finished …）。

### 4.3 网页服务 `board/server.py`

- `Demo` 装配：`EventStore`、`Control`、`NinePointSource`、`Manipulation`、`Modes`。
- GET：页面、`/control/status`、`/manipulation/status`、`/calibration/status`、`/modes/status`、`/api/v1/health|mode|job`、视频流等。
- POST 网页接口（`/control/*`、`/manipulation/*`、`/calibration/*`、`/modes/*`）：要求同源 `Origin` + `csrf` 令牌（令牌在 `/control/status` 里，页面自动带上）。
- POST 电脑端接口 `/api/v1/*`：不需要 csrf，靠模式会话编号授权（见第 6 节）。
- 启动时后台线程：摄像头采集；`modes.warm_dance_checks()` 预先计算并缓存两支舞的模型碰撞检查。

## 5. 主要功能流程

### 5.1 人工框选抓放（`/manipulation` 页，`manipulation_task.py`）

1. **冻结**：`capture` 同时保存一帧画面和六关节真实读数（`capture_mode=joint_snapshot_v1`，随臂相机，任意观察姿态）。
2. **标注**：用户在画面上标出方块顶面四角（或旋转框），再标一个放置点像素；也可选“只夹取”。
3. **定位**（`manipulation_geometry.locate`）：由冻结读数做正运动学得到相机位姿 → 像素射线与平面求交。投影平面先用手眼标定板面，再按“30 mm 方块四条顶面边的平均投影长度 = 30 mm”对本帧自校（`projection_source=block_size_fit`）；运动高度用安装板 80 mm 实测基准（`table_z_mm=0`）。
4. **规划**（`_build_plan`）：张开夹爪并到取物上方 → 接近抓取 → 夹持 → 抬升 →（抓放时）转移至放置点上方 → 下降放置 → 释放 → 撤离。每段用带夹爪方向约束的逆解（九点参考引导，`manipulation_guided.py`），同一段内需要变的关节合并为一次同步下发，并对“同步线性插值 + 20 ms 发送滞后包络”做 CAD 碰撞扫掠。相邻移动段若切角路径通过检查则提前 300 ms 衔接（`blend_next_ms`）。
5. **电脑端加速（可选）**：`pc_plan()` 把配置、标定、目标、九点参考发给 `pc/plan_server.py`；两端代码指纹（`planner_version.code_digest`）一致才受理。开发板用 `manipulation_replay.py` 重放复核全部条件（3 核并行扫掠），任何一项不符或电脑没开就改为本地规划。计划里的 `planner` 字段记录来源。实测：电脑+复核约 4 s，本地约 15 s。
6. **预览**：页面显示三维动画、全部步骤、每步是“提前衔接 / 到时直接下一步 / 停稳回读”、预计用时、计算来源。
7. **执行**（`run`）：用户点“确认执行以上步骤”。执行时只核对输入指纹与审计散列（不重新规划）、执行前读数与冻结起点相差 ≤1°。然后：
   - 除最后一步外，每步用时到了就直接下发下一步，不停稳、不回读（2026-11-13 要求，夹爪开合 800 ms）；
   - 最后一步停稳回读：读取失败只记警告；偏差 ≤3° 记警告，>3° 判失败；夹持中夹爪被方块挡住不算偏差；
   - 单关节写入失败重发同一目标最多 2 次。
8. 结果写 `data/logs/events.jsonl`；“completed” 只代表指令全部下发，夹没夹到需人工确认。

### 5.2 识别模式（`/modes` 页 + `/api/v1`，`modes.py`）

用户在 `/modes` 预览会话全部限制并勾选“开启模式”，即授权该会话内有限次数的动作；电脑端再也不用逐次确认。

- **方块识别自动抓取 `block_grasp`**：电脑端调 `/api/v1/block/frame` 冻结一帧（画面 + 六关节读数）→ 自己识别 → `/api/v1/block/target` 提交该帧的像素检测（`corners`/`center`/`score`/`label`，**不得提交关节角**）。开发板走与 5.1 完全相同的定位、规划、执行。任务类型：`pick_place`（需要配置里的固定放置点 `destinations`，**目前设备上为空**，所以实际只能用 `pickup`，每会话 1 次）或 `pickup`（夹起抬升后保持夹持）。连续 5 次规划失败自动结束会话（`MAX_CONSECUTIVE_PLAN_FAILURES`）。
- **表情手势跳舞 `gesture_dance`**：电脑端调 `/api/v1/gesture` 只发动作名（如 `MUSIC_DANCE_ROUTINE`），开发板执行会话开启时已展示的那套动作；有次数上限、最短间隔、有效期。
- 会话在超时、次数用完、任一动作失败、开启时已存在的规则/代码/配置文件变化、网页关闭模式或电脑端 `/api/v1/stop` 时结束。

### 5.3 跳舞（首页“跳舞预设”卡片 + 识别模式，`dance.py` + `modes.py`）

- 预设在 `board/data/dances.json`（设备上以 `board/data/` 为准），代码默认值在 `dance.DEFAULT_DANCES`：
  - `MUSIC_DANCE_ROUTINE`“音乐舞蹈”：Zeta Education 教程 “Dancing With Music!”，26 拍，62 个越界值在模板里人工改为本机合法值；
  - `COURSE_DANCE_ROUTINE`“课程舞蹈”：课程《任务7：机械臂跳舞》，17 拍，4 个越界值改为边界值。
  - 两支都是 `keyframes`（逐拍绝对角），要求起始姿态为六关节 90°（设备上的“竖直”姿态按钮）。另有偏移类模板 `sway/nod/circle` 仍受支持但不是预设。
- `build_routine`：生成“第 0 步 到起始姿态（六关节目标）+ 每拍目标”，每个目标经 `arm.angle` 校验，任一越界整套拒绝。
- 预览/开始前用 CAD 模型检查每拍的同步插值与发送滞后包络（`check_collision`，结果缓存；开发板首次约 10～30 s，服务启动时后台预热）。
- 执行 `run_dance`：
  - 到起始姿态：先读六关节，±1° 内的跳过；全部到位直接开跳；否则需要动的关节同批在 300 ms 内到竖直，前提是 1～5 号读数齐全且从读数出发的路径通过 `check_start_move` 模型检查，否则不运动、本次失败。
  - 之后每拍同批下发，运动中不回读；“停止后续”只停未发出的拍子，不是急停。

### 5.4 手动调整与姿态按钮（首页，`control.py` + `saved_states.py`）

- 单关节：输入角度回车即下发（经 `arm.angle` 校验）。
- 姿态按钮：保存六个整数目标、六关节顺序、用时；点“确认依次调整到”逐关节执行。设备上有“竖直”（全 90°，顺序 4,3,2,5,6,1）等。

### 5.5 相机标定（`/calibration`，`charuco_*`）

ChArUco 板标定镜头内参与“随臂相机 ↔ link4”外参，只拍照和读数，不运动。结果供定位使用。详见 `docs/相机标定使用说明.md`。

## 6. 电脑端接口（`pc/armlink`）

`BoardClient(base_url)` 方法：`health()`、`mode()`、`job()`、`snapshot()`、`wait_for_mode(kind)`、`wait_job(job_id)`、`freeze_frame(session_id)`、`submit_block(session_id, frame_id, detection)`、`dance(session_id, routine, label, confidence)`、`stop(session_id)`。数据结构在 `armlink/types.py`（坐标一律原图像素，左上角原点）。

`/api/v1` 一览：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/health` | 服务、摄像头、实机/模拟 |
| GET | `/api/v1/mode` | 当前会话：类型、编号、次数、有效期、授权动作 |
| GET | `/api/v1/job` | 当前/最近任务状态 |
| GET | `/api/v1/frame.jpg` | 摄像头最新一帧（不冻结、不读舵机；`snapshot()` 用） |
| POST | `/api/v1/block/frame` | 冻结一帧（须带网页“开始识别夹取”给的 request_id；返回 jpeg_base64、frame_id、六关节读数） |
| POST | `/api/v1/block/target` | 提交像素检测 → 开发板定位、规划、执行（同一 request_id） |
| POST | `/api/v1/block/report` | 本次未提交的原因（没找到方块等），结束本次 |
| POST | `/api/v1/gesture` | 提交跳舞动作名 |
| POST | `/api/v1/stop` | 结束会话 |

完整说明与示例见 `docs/接口与合并指南.md`。

## 8. 运行、测试、部署

- **本机全模拟**（不连设备）：`.venv-mac/bin/python -B board/simulate.py --port 8092`，打开 `http://127.0.0.1:8092`。可加 `--pc-planner` 走电脑端规划流程。
- **测试**：`zsh tools/run_tests.sh`；或 `cd board && python -m unittest discover -s tests`（约 207 个），`node tests/*.cjs`（页面脚本），`cd pc && python -m unittest discover -s tests`。测试全部用假舵机，**不得连实机**。
- **Mac 环境**：项目根 `.venv-mac`（Python 3.9，numpy、opencv）。注意 Mac 走代理 127.0.0.1:7890，访问开发板要 `--noproxy '*'`。
- **电脑端规划**：`.venv-mac/bin/python -B -u pc/plan_server.py`（端口 8095；开发板默认请求 `192.168.137.101:8095`）。改了 `planner_version.PLANNER_FILES` 里的任何文件，电脑端和开发板都要更新并重启，否则指纹不一致会退回本地规划。
- **开发板启动**：`/root/miniconda3/envs/ros-arm-env/bin/python -B /root/jjt/board/start_service.py --enable-ros-planner --enable-real-control`（启动不读舵机、不运动）。停止：kill `data/server.pid` 和 `data/planner.pid` 里的进程。
- **部署惯例**（助手这样做）：核对设备上将被覆盖的文件与上次部署/git 版本一致 → 备份到 `/root/jjt/backups/<名称_时间>/` → `scp` 覆盖 → 校验 SHA-256 → 设备空闲且无模式会话时重启服务。`board/data/` 不随代码覆盖。
- Mac 启动器 `tools/mac/service.py` 会核对 `reviewed_sources.json` 里的文件指纹，不一致拒绝启动（当前因设备上 `web/modes.html` 被队友改过而会拒绝，见下）。

## 9. 规则文件与授权模型（讲解时必须说明）

- `AGENTS.md` 与 `机械臂操作准则.md` 按日期累积了用户的每一条要求，后面的条目可以取代前面的（文中会写明“此条取代……”）。代码执行时对这两个文件做散列，改动会让进行中的预览和会话失效。
- 授权来源只有用户在网页上的当次操作：手动调整的“确定”、姿态按钮的“确认依次调整到”、抓放计划的“确认执行以上步骤”、跳舞卡片的“开始跳舞”、`/modes` 的“开启模式”。**AI agent 不得替用户点击这些按钮、开启模式，或运行会触发实机运动的电脑端程序。**
- 统一不变的底线：整数角度、配置范围、统一控制层校验、硬件锁、版本/审计核对、请求去重、异常停止后不自动重试/复位/松爪；Ctrl+C 和“停止后续”都不是急停。
- 已放宽的地方（都由用户明确要求并写入规则）：随臂抓放中间步骤不停稳不回读、读数失败只记警告、回读 3° 容差、单关节写入失败重发 2 次、跳舞前 300 ms 同步回竖直。

## 10. 当前状态与已知问题（2026-11-15）

- **设备上跳舞名称仍是旧的**（`music` / `course`）：队友 11-15 把名称改为 `MUSIC_DANCE_ROUTINE` / `COURSE_DANCE_ROUTINE`，代码已在 GitHub，但还没部署到开发板（当时开发板离线）。部署前电脑端用新名称会被拒绝。
- **设备上 `web/modes.html` 被方块识别同学直接改过**（11-09，加了“PC 识别抓取”浮动面板，硬编码调用 `192.168.137.102:8099`，旁边留有 4 个 `.bak`），不在 git 里。不是控制逻辑，但下次覆盖部署会丢失；也因此 Mac 启动器的指纹检查会拒绝启动。
- **`arm.checked_call` 的输出捕获有并发问题（未修）**：它重定向的是整个进程的 stdout/stderr，网页服务线程恰好在这期间打印访问日志时，会被误判为舵机读/写失败（日志里出现错误文字是 `GET /api/v1/health ...` 的读取失败）。读取误判只多一条警告；写入误判会触发重发，极端情况下连续 3 次会无故停止。电脑端每 2 s 轮询时更明显。
- **固定放置点 `destinations` 为空**：识别模式只能用 `pickup`（夹起不放）。
- **远距离抓取**：队友的自动抓取方块多在离底座 270～300 mm（接近伸展极限），人工测试在 185～210 mm 都成功；远距离失败的原因尚未单独验证。
- **规划服务地址写死为 `192.168.137.101:8095`**（`board/pc_planner.py`），换电脑需改地址；Windows 上的规划服务未实测。
- **语音模块需要 Python ≥3.10**，Mac 的 `.venv-mac`（3.9）跑不了它的测试。
- CAD 碰撞模型、相机定位、各处“模型检查通过”都是估计，**未做独立精度验收**；“completed” 不等于夹取成功。
